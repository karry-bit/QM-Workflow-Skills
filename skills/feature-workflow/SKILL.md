# Feature Workflow

本 Skill 不绑定任何一个仓库。规范文件、介绍文件、模块边界都以当前打开的项目为准。

用户发来一句话后，先判断行为，再进入对应路径。界面修改先复用项目已有实现。没有可复用实现时，按下面的阶段进入对应前端 Skill，不要把全部 Skill 连着跑完。这些 Skill 不合适时，再联网查找资料后修改。

## 读项目

1. 先读代码。
2. 自己在当前项目里找介绍文件，不向用户追问文件名。先总结这份介绍，再和代码对照，判断内容是否大致一致。
3. 找不到介绍文件时，根据代码写一份总结，交给用户确认。
4. 介绍文件和代码不一致时，只列出差异，然后询问是否要改介绍文件。用户同意后才改。
5. 再读该项目的规范文件，例如 `版本.md` 和项目架构说明。

## 改界面

1. 先复用项目里已有的组件、样式和写法。
2. 只有用户明确声明不用项目已有实现时，才跳过第 1 步。
3. 没有可复用实现时，按任务进入对应阶段。同一阶段内按列出的先后读取。不要把全部前端 Skill 连着跑完。
4. 这些 Skill 不合适时，再联网查找资料，然后修改。

同一次改动既有界面又有功能逻辑时，先走「改功能」：问清楚并确认方案后才执行。执行时再改界面。

### 已有界面

1. `style-extractor`：从现有页面抽出字体、颜色、间距和组件规则。
2. `redesign-skill`：只改现有界面，不整页重写。

### 还没有可复用实现

1. `ui-design`：先定层级、布局和规格。网页和小程序都走这里。
2. `ui-ux-pro-max`：按产品类型选风格、配色、字体和交互规则。
3. `design-system`：要形成可复用的颜色、字号、间距时再写 token。
4. `frontend-design`：把方向收成具体的视觉做法。
5. `taste-skill`：只用于落地页、作品集、整页改版。后台、表格、多步业务界面不用它。

### 品牌、出图或 Stitch

只有任务本身是品牌、出图或 Stitch 时才进入，按这个先后：`brand`、`brandkit`、`banner-design`、`imagegen-frontend-web` 或 `imagegen-frontend-mobile`、`image-to-code-skill`、`stitch-skill`。普通改界面跳过。

### 写界面

1. `web-design`：营销页、介绍页。先出设计说明，用户确认后再写页面。
2. `web-development`：产品界面的实现、联调和修改。
3. `ui-styling`：项目已经在用 Tailwind 或 shadcn 时。
4. `antd`：项目已经在用 Ant Design 时。

`design` 会再转到 `brand`、`design-system`、`ui-styling`，不放进必经顺序。

### 写完再打磨

1. `make-interfaces-feel-better`：间距、边框、阴影、图标、悬停和动效。
2. `web-design-guidelines`：按界面规范做一次检查。

## 改功能

1. 不要先写代码。
2. 一次只问一个问题。可以给选项；每个选项都写成确认后能原样写入方案的句子。
3. 问清楚后给出修改方案和验收标准。用户同意或确认后才开始修改。
4. 修改完成后，自动按验收标准跑一遍。
5. 在当前项目根目录写 Markdown 记录验收标准。同一模块的同一功能共用一个文件，文件名格式：`模块名-功能名修改.md`。后续修改追加进这个文件。正文标题格式：`1.某模块-某某功能修改`。验收标准最后写明本功能修改涉及哪个模块。若这次是在改已有验收标准，就更新原文，不另起一条。
6. 白盒、黑盒都要做。
7. 最后检查改动是否影响其他功能。只沿直接依赖扩展：
   - 改了 A 模块功能 1，B 模块功能 2 依赖 A 的功能 1，则 B 的功能 2 必须进入本次验收。
   - C 模块功能 1 只依赖 B 的功能 2 时，默认不进入本次验收。
   - 只有 A 的功能 1 确实影响了 B 的功能 2，才把 C 的功能 1 加入验收。
